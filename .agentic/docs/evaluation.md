# 구현 평가 기준

구현 평가는 다음 순서로 판단합니다.

```txt
기능 정확성
→ 테스트 품질
→ 코드 구조
→ 의존성 방향
→ 변경 용이성
→ 에러 처리
→ UX/접근성
→ 정적 품질
```

## 1. 기능 정확성

Pass 조건:

```txt
스펙에 정의된 기능이 모두 동작한다.
정상 시나리오가 통과한다.
예외 시나리오가 통과한다.
스펙 외 기능을 추가하지 않았다.
```

Fail 조건:

```txt
핵심 기능이 누락되었다.
테스트가 통과해도 실제 사용자 시나리오가 실패한다.
스펙을 임의로 변경했다.
```

## 2. 테스트 품질

Pass 조건:

```txt
도메인 함수 테스트가 있다.
저장소 테스트가 있다.
상태 관리 테스트가 있다.
컴포넌트 이벤트 테스트가 있다.
핵심 사용자 시나리오 테스트가 있다.
실패 케이스 테스트가 있다.
```

## 3. 코드 구조

Pass 조건:

```txt
도메인 로직과 UI가 분리되어 있다.
저장소 로직과 상태 관리가 분리되어 있다.
컴포넌트 책임이 명확하다.
함수는 하나의 책임만 가진다.
중복 코드가 과도하지 않다.
```

## 4. 의존성 방향

허용 방향:

```txt
UI → 상태 관리 → 도메인 로직 → 타입
UI → 상태 관리 → 저장소
저장소 → 타입
도메인 로직 → 타입
```

금지 방향:

```txt
도메인 로직 → UI
도메인 로직 → 저장소
타입 → 컴포넌트
저장소 → 컴포넌트
하위 계층 → 상위 계층
```

## 5. 변경 용이성

Pass 조건:

```txt
새 필드를 추가할 때 수정 범위가 명확하다.
LocalStorage를 API 저장소로 바꿀 수 있는 경계가 있다.
기존 테스트를 과도하게 수정하지 않아도 기능 확장이 가능하다.
```

## 6. 에러 처리

Pass 조건:

```txt
잘못된 입력을 처리한다.
저장소 데이터 파싱 실패를 처리한다.
저장 실패 시 앱이 깨지지 않는다.
사용자가 이해할 수 있는 에러 메시지를 제공한다.
```

## 7. UX/접근성

Pass 조건:

```txt
키보드로 주요 동작이 가능하다.
input에 label이 있다.
button에 접근 가능한 이름이 있다.
checkbox가 어떤 Todo와 연결되는지 알 수 있다.
빈 상태 메시지가 있다.
완료 상태가 시각적으로 구분된다.
```

## 8. 정적 품질

Pass 조건:

```txt
타입 에러 0개
린트 에러 0개
포맷 일관성 유지
테스트 전체 통과
빌드 성공
불필요한 console.log 없음
```
